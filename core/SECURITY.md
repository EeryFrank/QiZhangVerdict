# 七章的裁决 / QiZhang's Verdict core

`GuardService` is a Java 8 library with no runtime dependencies. `:core:securityTest` executes dependency-free security integration tests. All public service operations are thread-safe. Platform adapters must call `openSession` using the server-observed literal IP and authenticated UUID, `confirmSession` only for a successful join, and `closeSession` on disconnect. An offline server UUID is not proof of a registered or purchased account. Do not trust a forwarded IP unless your proxy connection is separately authenticated and restricted.

IP limits count exact IP addresses; IPv4-mapped IPv6 normalizes to IPv4. The strict defaults require the companion and a scoped device digest (`companion.required=true`, `device.required=true`). Up to three accounts can connect from one IP (`limits.max-online-per-ip=3`), but only one verified session can use the same IP and reported device (`limits.max-online-per-ip-device=1`). Device-slot checks are atomic; reissuing a challenge does not release an occupied slot, and disconnect does. Different IPs are not combined by this concurrency rule. IPv6 privacy-address or proxy rotation is not prevented. NAT/shared households may legitimately share an address. Both IPv4 and IPv6 CIDRs are supported; deny rules take precedence. Hostnames, IPv6 zone identifiers, shorthand IPv4 and ambiguous leading-zero IPv4 forms are rejected. No DNS resolution occurs.

Only confirmed joins enter the rolling account history. Concurrent pending joins reserve quota until closed or a 30-second expiry, preventing simultaneous quota bypass without permanently recording failed attempts. The service bounds active reservations (65,536), stored IPs (100,000), and account/IP pairs (1,000,000); reaching capacity denies new storage allocations. Join-rate data is transient and bounded to 4,096 LRU IP buckets and 100,000 timestamps; distributed IP rotation can evict buckets, so this is not a DDoS firewall. Use network-level connection controls independently.

`guard.properties`, `blacklist.tsv`, and `rules.tsv` reload together only after all validate. Existing sessions/history are retained. Unknown properties and malformed rules fail visibly. Managed rule changes are atomically written before becoming live. `listRules` includes default entries with `legacy:kind:value` IDs, so `removeRule` can delete them as well. Managed rules have UUID IDs, BLACK/WHITE lists, MOD/PACK/BRAND/PLAYER/DEVICE kinds, and EXACT/GLOB matching. Only `*` and `?` are wildcards; the bounded dynamic-programming matcher does not execute regular expressions. A WHITE match permits only that matching item; it cannot globally exempt other mods or bypass a persisted account/device ban. PLAYER exact rules use UUIDs. File actions cap per-rule actions: global OFF disables blacklist checks; ALERT downgrades DENY to alerts; DENY respects the default rule's own action. `automation` is an exact mod-ID rule category, ALERT by default. Pack names and brands can be renamed and are not cryptographic identifiers. There is no claim of an exhaustive cheat catalogue. Adapters should request fresh reports after rule changes; brand-only changes require rechecking the observed brand or reconnecting.

`accounts.state` version 2 stores observed IPs, UUIDs, last successful join timestamps, server-scoped device digests, account/device associations and bans together. Version 1 account history is readable. Restrict the data directory to server administrators. No original installation ID, MAC, serial number, file content or process list is stored. Old IP/account history is pruned at login/maintenance; device associations and bans remain until administrative maintenance, so their retention must be disclosed. Associations are bounded to eight devices per UUID and one million pairs overall. Saves snapshot under a lock, write/fsync a sibling temporary file, and atomically replace the state; unsupported atomic replacement is an explicit error, retaining the prior file. A corrupt state file causes startup failure rather than silently resetting limits. Save errors must be logged by adapters and retried while `isDirty()` remains true. No cross-process sharing of a data directory is supported.

Companion reports and device digests are untrusted client statements. A changed client can replace or copy the digest, hide mods, or fabricate an empty inventory. The digest is a client-side SHA-256 identifier scoped by the server's persistent public random identifier, not trusted hardware attestation. `server-id.txt` holds this 256-bit scope and every challenge carries it; the same server's different domain names/IP addresses/ports therefore do not create different identifiers for the unchanged companion. Preserve this file in backups and migrations; deleting/replacing it changes every device digest and invalidates its relationship to old device bans. Independently created servers receive independent scopes. Changing the local installation identifier or client can still change the digest. Secure random, single-use 256-bit nonces prevent stale-packet replay, not forged clients, changed binaries, renamed mods, hidden mods or pack manipulation. Response attempts consume the outstanding nonce, except up to two well-formed responses to the immediately previous nonce during an administrator rechallenge: those return denied `STALE_REPORT`, do not consume the new nonce, do not extend its deadline and must not release the adapter's waiting gate. Other mismatches consume the current challenge; the old nonce can never satisfy a new challenge. Protocol version 2 uses strict UTF-8, is bounded to 30,000 bytes, validates list counts/text sizes/trailing bytes, and owns immutable list copies. Version 1 reports are rejected rather than allowing a missing digest to bypass the strict policy. Required reports expire even if the client never registers the channel. Reissuing an outstanding challenge does not extend its deadline. An administrator can manually disable both required options for optional companion mode, reducing enforcement; optional report absence never causes a timeout kick.

The default `sanctions.on-deny=BAN` permanently records explicit blacklist/VM denials against the UUID, all known device digests, and known accounts connected through those device associations. A future account reporting a banned digest is denied and linked under BAN policy. `sanctions.on-deny=KICK` leaves these automatic bans disabled. IP policy, rate limits, IP/device concurrency, missing/incomplete/malformed reports, nonce errors and unknown VM indicators never cause automatic permanent bans. `checkBrand(UUID, brand)` enforces sanctions; the old `checkBrand(brand)` is a pure check. Without a prior or current report, a brand-triggered ban can only ban the known account; the server cannot invent an unknown device ID. Automatic bans mark the state dirty for adapter background persistence; administrative `ban`/`unban` flush immediately and surface I/O errors. A save failure preserves in-memory policy and is retryable; it is not a successful durable write. `unban(UUID)` and `unban(device:<digest>)` intentionally remove their own record independently. To fully admit an associated account/device, administrators must remove all relevant ban records. Wrong or spoofed client identifiers can associate innocent accounts, so administrators must review evidence before treating an automatic ban as reliable proof.

VM detection is best-effort self-reporting. The default `vm.action=DENY` requires `companion.required=true`; optional companion mode must also change VM action to ALERT or OFF. Recognized VM categories are `virtualbox`, `vmware`, `qemu`, `kvm`, `xen`, `parallels`, `hyper-v-guest`, `cloud-vm`, and `bhyve`. Empty indicators do not prove a physical machine. Unrecognized/unknown/probe-failure indicators only alert. Hypervisor presence alone only alerts because physical Windows systems using VBS can report it. Administrators must not treat any of these checks as tamper-resistant attestation.

Managed rules are capped at 10,000 and have a shared one-million-step evaluation budget per report. Pathological wildcard tables are rejected with `RULE_EVALUATION_LIMIT`, without a permanent ban, so a client cannot force unbounded rule processing. Account and device ban tables are each capped at one million records; a graph update that would overflow either applies no new bans and denies the triggering connection. A persisted snapshot exceeding 128 MiB is not written because it would exceed the loader's safe file bound. Adapters should call `bannedSessions()` every second and disconnect/close those sessions to enforce newly linked bans on accounts that are already online. `recheckSession()` revalidates IP rules and existing account/device/PLAYER restrictions after reload without refreshing account history; lower concurrency limits apply at the next login/report.

Movement/combat behavior checking and anti-Xray chunk obfuscation require independent supported server implementations. A mod-name blacklist cannot detect arbitrary cheating behavior or prevent an Xray renderer from seeing already-sent ores. No remote telemetry, file scanning, process scanning, MAC collection or hardware serial collection is implemented.
