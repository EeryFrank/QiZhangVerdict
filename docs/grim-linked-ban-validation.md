## 本次实际验证的链路

先让两个合成账号分别提交同一合成设备码，历史账号退出，处罚目标保持在线。目标在完整默认策略下正常在线超过 22 秒后，以 160 毫秒间隔发送重复 `held_item_slot` 数据包。两版本都发送 121 个包，由真实 Grim `BadPacketsA` 检查产生控制台 `x20` 至 `x120` 告警，再执行模板中的 `120:0 qzverdict ban %player% Grim-BadPackets`。

脚本核对目标因确切的 `Grim-BadPackets` 原因断开，并直接读取测试目录持久化状态，要求恰好两个账号和一个设备的封禁，三个条目的理由全部来自本次 Grim 命令。状态原文件不公开；重启日志独立显示 `accountBans=2, deviceBans=1`，协议结果记录对应状态断言。

随后正常 `stop` 并以相同目录、配置和端口启动第二个服务器进程，验证：

- 原目标换设备后仍被账号封禁拒绝，历史关联账号同样拒绝。
- 新账号报告被封设备时拒绝；同 IP 的独立设备账号仍可进入。
- 显式解除三个账号和一个设备的四项封禁后，原目标恢复准入，持久化封禁条目清零。

此处第三个账号的封禁来自重启后尝试使用已封设备。账号与设备需要分别解封，符合现有管理命令语义。

整个过程没有缩短默认 20 秒报告期限、放宽账号或 IP 配额、关闭设备验证，也没有降低 Grim 示例阈值。Guard 默认配置 SHA-256 为 `47310c31b47287ab805bfdbf8ddddf80e8169385bd9c862239a0a0075644da4e`：配套报告和设备码必需、VM 已知证据拒绝、同 IP 最多 3 在线、同 IP 同设备最多 1 在线、720 小时内最多 5 个账号、每分钟最多 20 次尝试。

## 保留的告警与验证边界

1.20.1 的 Grim 2.3.71 版本更新检查解析新版版本号时出现 `NumberFormatException`。1.21.1 的协议客户端在物品组件解析中出现带 `ArmorTrimMaterial`／`SlotComponent` 的 `PartialReadError`，最终处罚阶段 2 次、重启阶段 3 次。两类信息均保留在原日志；当前断言与正常退出实际完成，不代表更新检查或全部物品协议没有问题。服务端的离线模式、缺少 `api-version`、终端与 SIMD 告警同样没有删除。

这次证明的是固定依赖下的一条真实 Grim 检查→管理命令→账号／合成设备关联封禁→重启／解封链路，不证明全作弊检测准确率、误报率、反绕过、移动／战斗检查、性能、真实 VM 检测或硬件可信证明。历史关联账号在触发时离线，本轮没有覆盖“已在线关联账号立即断开”的独立情况。完整默认策略保持不变，也不等于本套用例穷举了所有 IP 配额和黑名单分支；超过 22 秒的正常准入不是无报告客户端超时测量。模组端、图形客户端、代理转发和生产身份认证需使用各自证据。
